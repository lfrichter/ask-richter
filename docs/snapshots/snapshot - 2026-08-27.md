## 1. 🌐 M15 — Multilingual Response Alignment (Alinhamento Multilíngue de Respostas)

### 1.1 Contexto e Resolução do Problema
Anteriormente, o prompt do sistema no manipulador de chat (`apps/frontend/src/app/api/chat/route.ts` e `apps/backend/src/index.ts`) continha a regra fixa:
`1. IDIOMA: Responda SEMPRE em Português do Brasil, independentemente do idioma do contexto.`

Essa instrução forçava o modelo a responder em português mesmo quando recrutadores ou lideranças técnicas internacionais faziam perguntas em inglês (ex: *"Could you give me last companies experience from him"*).

### 1.2 Especificação M15
A especificação M15 estabelece o alinhamento estrito do idioma de saída com o idioma da pergunta do usuário:

1. **Prioridade Absoluta do Idioma do Usuário:** O idioma da mensagem do usuário determina a língua de resposta (`Inglês -> Inglês`, `Português -> Português`, `Espanhol -> Espanhol`).
2. **Desacoplamento do Idioma do Contexto:** O texto recuperado do banco de dados/vector store serve estritamente como **fonte de evidência factual**. O idioma em que o contexto está escrito (ex: português) não altera o idioma de resposta do LLM.
3. **Preservação da Pipeline RAG:** Não foram realizadas alterações na etapa de recuperação semântica, nos embeddings (`gemini-embedding-2`), no índice vetorial ou na busca por similaridade.

### 1.3 Atualização das Regras do Prompt do Sistema
```text
REGRAS OBRIGATÓRIAS E INEGOCIÁVEIS:
1. IDIOMA / LANGUAGE ALIGNMENT: Responda SEMPRE no mesmo idioma da pergunta do usuário (Answer ALWAYS in the exact same language as the user's message). Se a pergunta for em Inglês, responda em Inglês. Se for em Português, responda em Português. Se for em Espanhol, responda em Espanhol. O idioma da mensagem do usuário tem prioridade absoluta sobre o idioma do contexto recuperado. O contexto recuperado serve exclusivamente como fonte de evidência factual.
```

## 2. 🛣️ Invariantes de Roteamento de Produção (Defesa Anti-Render)

### 2.1 Diagnóstico do Roteamento
Após a migração para RAG Serverless na Vercel (ADR-0007 / ADR-0008), observou-se que o navegador continuava enviando chamadas para `https://ask-richter-backend.onrender.com/api/chat`.

**Causa Raiz:** O Next.js substitui variáveis `NEXT_PUBLIC_*` estaticamente no bundle JavaScript durante a compilação. Como a variável `NEXT_PUBLIC_API_BASE_URL` estava cadastrada no painel da Vercel apontando para o Render, o valor `https://ask-richter-backend.onrender.com` foi "chumbado" (hardcoded) no bundle estático de produção.

### 2.2 Solução Arquitetural Aplicada (Planos L, M, N, O, P)
1. **Sanitização em Tempo de Execução:** Em `apps/frontend/src/app/page.tsx` e `supabase-unfreeze-modal.tsx`, foi implementada uma verificação que descarta qualquer URL contendo `onrender.com` e força o uso de caminhos relativos:
   ```typescript
   const rawUrl = process.env.NEXT_PUBLIC_API_BASE_URL || '';
   const apiBaseUrl = rawUrl.includes('onrender.com') ? '' : rawUrl.replace(/\/$/, '');
   ```
2. **Rotas Relativas Nativas Vercel:** Em ambiente de produção Vercel, todos os endpoints do frontend (`/api/chat`, `/api/supabase/status`, `/api/supabase/restore`, `/api/ready`) operam utilizando **rotas relativas**, eliminando dependência do Render.
3. **Commit & Push de Produção:** Alterações comitadas e enviadas para a branch `main` no commit `de6e688`.

## 3. 🔍 Aprimoramento da Probe do Supabase Status (`/api/supabase/status`)

### 3.1 Correção de Falsos Erros HTTP 401
- **Problema:** A rota de status consultava o endpoint OpenAPI de introspecção do Supabase (`/rest/v1/`) passando a chave `anon`. Como o Supabase restringe a raiz `/rest/v1/` para a chave `service_role`, a chamada retornava HTTP 401 (`UNAUTHORIZED_INVALID_API_KEY_TYPE`), gerando falso aviso de falha.
- **Solução Aplicada:**
  1. Integração com a **Supabase Management API** (`getSupabaseManagementProjectStatus()`), validando previamente se o projeto está em estado `ACTIVE_HEALTHY`.
  2. Priorização da chave `SUPABASE_SERVICE_ROLE_KEY` na requisição REST.
  3. Se a Management API confirmar `ACTIVE_HEALTHY` e o endpoint REST retornar 401 devido a restrições de chave, o classificador valida o status como `READY` (HTTP 200).

## 4. ⏱️ Calibração do Timeout de Fetch do Cliente (`AbortError` Fix)

### 4.1 Problema Identificado
Durante a execução de buscas em produção, o navegador exibia o erro:
`Erro ao chamar ou processar a API: AbortError: signal is aborted without reason`

### 4.2 Causa Raiz & Solução
O temporizador de cancelamento (`AbortController`) em `apps/frontend/src/app/page.tsx` estava configurado em **6000ms (6 segundos)**. Como o ciclo completo de RAG Serverless (cold start da Serverless Function + embedding no Gemini + busca vetorial + geração de resposta no `gemini-3.6-flash`) leva de 3 a 8 segundos, requisições que levavam mais de 6s eram abortadas prematuramente pelo próprio navegador.

- **Ajuste Aplicado:** O timeout de requisição foi ampliado de 6s (6000ms) para **30s (30000ms)** em `page.tsx` (Commit `860b6ea`), permitindo a conclusão de respostas mais complexas sem interrupção.
